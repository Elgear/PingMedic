# PingerApp Distribution Security

## Official downloads

The only official public PingerApp binaries are installers published under the repository's GitHub Releases page:

https://github.com/Elgear/PingerAPP/releases

Do not treat repository ZIP downloads, binaries re-hosted on third-party sites, or installers received through file-sharing services as official releases.

## Release assets

Each release should publish only the end-user installer and its SHA-256 checksum file:

- `PingerApp_Setup_<version>.exe`
- `PingerApp_Setup_<version>.exe.sha256`

The checksum is generated by the GitHub Actions release workflow from the exact installer that is uploaded.

Windows users can independently verify an installer with:

```powershell
Get-FileHash .\PingerApp_Setup_<version>.exe -Algorithm SHA256
```

The result must match the value in the corresponding `.sha256` release asset.

## Code signing

Public releases should use Authenticode signing when a trusted signing identity is available. The signing private key must never be committed to the repository or stored as an ordinary source file.

Preferred options, in order:

1. SignPath Foundation sponsored signing if PingerApp is accepted as a qualifying open-source project.
2. A managed trusted signing service if sponsored signing is not available.
3. A traditional CA-issued OV code-signing certificate stored in an appropriate hardware-backed or managed signing system.

Self-signed certificates are useful only for development or environments where the certificate can be explicitly trusted. They are not a substitute for public code signing.

When production signing is enabled, sign both the packaged application executable and the final installer. Releases should be timestamped so signatures remain verifiable after certificate expiry.

## What signing protects

A valid digital signature provides two important properties:

- authenticity: the binary was signed by the expected publisher;
- integrity: the signed file has not been altered after signing.

Signing cannot prevent a malicious third party from creating a different file and calling it PingerApp. Users should therefore obtain releases only from the official GitHub repository and verify the publisher/signature and checksum when appropriate.

## Build and release controls

The release workflow should continue to:

- build on GitHub-hosted Windows runners;
- derive the release version from `PingerApp/version.py`;
- build the PyInstaller application before the Inno Setup installer;
- generate the SHA-256 checksum after installer creation;
- upload the installer and checksum together;
- publish release assets from the workflow rather than from a developer workstation;
- use least-privilege GitHub Actions permissions wherever practical.

For stronger supply-chain assurance, production workflows can additionally pin third-party GitHub Actions to reviewed commit SHAs and use branch protection/rulesets so release-affecting changes reach `main` through reviewed pull requests.

## Security and issue reporting

Application bugs and feature ideas should be reported through GitHub Issues:

https://github.com/Elgear/PingerAPP/issues

Potential security vulnerabilities should follow the process in `SECURITY.md` rather than being disclosed publicly before they can be assessed.
